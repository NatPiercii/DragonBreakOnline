# Server authority: what must live on the server, what cannot, and the migration order

Written 2026-09-17 from a 10-agent audit of the fork (relay path traced end to end, four area sweeps,
three adversarial challenges). Answer to the rule Jake set: "everything server side, relayed to everyone,
nothing non-player-operated on a client". Read with serverNPC_REBUILD.md and the C++ session in CHECKLIST.md.

## The rule, restated for this engine

THE RULE, CORRECTED FOR THIS ENGINE

Jake's version: "Everything needs to be server side for all logic so it is translated between each client. If it is client relayed, it needs to be relayed to everyone. Anything that is not player operated needs to be server side."

The instinct is right and the direction is right. It needs three words instead of one, because in SkyMP "server side" collapses two different things that have different answers.

---

1. AUTHORITY IS ALWAYS SERVER-SIDE. Every rule, every verdict, every piece of persistent state, every outcome. Whether a strike landed. Whether a target is valid. Whether a craft is legal. Who owns what. Who may bind whom. How much damage. Who is dead. There is no case in this project where a client legitimately holds a rule. If a client decides it, it is not a rule — it is a request.

2. EXECUTION IS OFTEN CLIENT-SIDE, AND THAT IS NOT AN EXCEPTION. There is no navmesh, no collision and no AI on the server, and the only motion it can originate is a teleport delivered to one viewer. So the engine must perform locomotion, animation, raycasts and anything needing physics. The client is the HANDS. It is never the JUDGE. When you are tempted to leave something on a client, apply this test: the engine must perform it is licence for the MOTION only, never for the VERDICT. Occupancy, hostility, death, ownership and validity are verdicts even when the thing they describe is a movement.

3. REPLICATION IS THE SERVER'S RESPONSIBILITY, NOT A SIDE EFFECT. "The owner's client did it" is not replication. There are exactly three channels that reach other players, and every visible fact must ride one of them:
   (a) the hosted movement sample — position is read live off the reference every ~130 ms and the raw bytes are forwarded to that actor's listeners, so anything that moves a reference is replicated for free, including translateTo;
   (b) a neighbour-visible property (mp.makeProperty(name, true)) — this is how ff_hostile and ff_adminModes already work and is the right home for identity, ally state, equipment and any other fact every client must agree on;
   (c) a server-issued broadcast packet (the dboGlow pattern).
   Anything not on one of those three is owner-only, whatever it looks like on your screen.

4. WHOEVER HOSTS AN ACTOR IS ITS AUTHORITY IN PRACTICE — they move it, hit with it, cast with it and activate as it. Host must therefore be granted by server policy, never won by a race. Treat every host grant as a privilege the server issues and logs.

5. A CLIENT-SIDE BLOCK IS AN OPTIMISATION, NEVER AN ENFORCEMENT. Write it when the engine misbehaves without it, feed it from the server, and make the server re-check the outcome independently. playtest.js is the template: the server sends the door list, the client blocks the door so the engine does not start a cell load, and the server bounces anyone outside the region on a timer regardless. A patched client buys itself a few seconds.

6. WHEN A CLIENT MUST BE THE ONLY WITNESS, LET IT REPORT EVIDENCE, NEVER AN OUTCOME. The reading mini-game is the pattern and it is already in gamemode.js: the server generates the shuffle, the client returns a permutation, the server checks it. The client holds the puzzle and not the answer. Labour and skinning got this wrong by asking the client for a SCORE; craftedExtrasSystem got it right by accepting a REPORT and re-planning it against inventory the server actually holds. Anything a client reports must also be bounded — its own actor and the actors it hosts, with a cap and a rate limit — because an unbounded report is a primitive handed to a file the player owns.

---

THE TWO TESTS, for anything new:

  Could a player who edited the client bundle change the outcome? If yes, the authority is in the wrong place.
  Would a second player see it if the acting player's client froze? If no, it is not replicated.

Both must be no and yes respectively before a feature is finished.

---

AND THE THING THE TEAM SHOULD STOP SAYING: "the server re-checks the distance, so it is contained." It is not, yet. The only movement validation is a single per-packet delta test with no rate limit, so the position every proximity rule reads is whatever the client last wrote. Once movement is rate-validated, that sentence becomes true and about eight other gates become real at the same time. Until then, distance is advice. (Update 2026-09-19: the rate check is written and waiting on a CI build, migration 2 below. It counts once it is running with `"enforce": true`, not before.)

## Is "everything server side" achievable?

SHORT ANSWER: No, not literally — but Jake's rule is 90% achievable, and the 10% that is genuinely impossible is much smaller than the amount of logic currently sitting on clients. The rule is right; it just needs to be split into three words instead of one: AUTHORITY (always server), EXECUTION (often client), REPLICATION (always the server's responsibility to guarantee).

WHAT CAN BE AUTHORITATIVE — all of it, with no exceptions:
- Rules and verdicts. Whether a strike landed, whether a summon may exist, whether a target is valid, whether a craft is legal, whether an arrest holds, whether a dungeon is cleared. None of these need an engine.
- Persistent state and ownership. Inventory, gold, housing claims, mastery, factions, companion ownership, lease membership, perks. The server already owns most of this; the exceptions (Twin Souls, character progress) are accidents, not constraints.
- Outcomes. Damage is already computed server-side (ActionListener.cpp:1893-1900 CalculateDamage -> NetSetPercentages) and health/magicka/stamina are readable AND writable from the gamemode today via the `percentages` property (PercentagesBinding.h:7, .cpp:26-36 reads actorValues.{health,magicka,stamina}Percentage; Set() clamps to [0,1] and fans out with NetSetPercentages). Death is authoritative (MpActor::Kill -> SendAndSetDeathState). Position is authoritative in the sense that SetPos is the server's record and drives subscriptions.
- Visibility of state to other players. Any fact can be published to every neighbour as a neighbour-visible property (mp.makeProperty(name, true) -> SendMessageToActorListeners, MpObjectReference.cpp:775-791). ff_hostile and ff_adminModes prove the pattern works. Anything currently known to one client only is a choice, not a limit.

WHAT MUST EXECUTE ON A CLIENT — and why, from the relay facts:
- Locomotion and pathing. There is no navmesh, collision or AI server-side (libespm parses NAVM vertices; nothing consumes them). The only server-originated motion is MpActor::Teleport, delivered to exactly ONE user via GetActorToSendTo (MpActor.cpp:1635-1648). The server therefore cannot walk, nudge or path anything; it can only relocate it, for one viewer, and let that viewer's stream carry the result.
- Animation. The server never generates an animation; it forwards the bytes a client sent (ActionListener.cpp:510 SendToNeighbours) and stores the last one (PartOne.cpp:806).
- Anything requiring collision or line of sight: crosshair raycast, fall/trap detection, seat reachability at the geometric level.
- Engine-computed personal mechanics keyed on local actor values: spell magicka cost, tempering/alchemy quality, lockpicking, sneak detection. Magicka and stamina are not even on the wire between clients.

THE CRUCIAL POINT ABOUT RELAY, which resolves the second half of Jake's rule: a hosting client's movement sample IS already relayed to everyone. getMovement reads the reference's live position straight off getPositionX/Y/Z (movementGet.ts:58, objectReferenceEx.ts:25-27), sendInputsService ships it for every id in storage['hosted'] on the same path as the player's own (sendInputsService.ts:110-125, :140), and ActionListener::SendToNeighbours forwards the raw bytes to that actor's listeners BEFORE validation (ActionListener.cpp:435 vs :452). So "the client moved it" and "everyone saw it move" are already the same thing for position. What is NOT relayed on that path: equipment (sendInputsService.ts:282-284 early-returns for any hosted id, and OnUpdateEquipment resolves the actor by user so it structurally cannot carry an NPC's gear, ActionListener.cpp:546-552), actor values other than the health riding the movement packet (OnChangeValues has no SendToNeighbours), combat state (no message exists), faction/ally/aggression setup, and anything a client decides privately.

So the honest formulation is: the server can own every RULE and every piece of STATE in this project. It can never own MOTION. And the gap between "a client executed it" and "everyone sees it" is closable in every case — either the fact rides the hosted movement sample, or it becomes a neighbour-visible property, or the server re-broadcasts it as a dbo* packet. There is no case in this codebase where a client legitimately holds a rule.

ONE THING THAT IS WORSE THAN THE RULE ASSUMES: several server-side gates that look authoritative are not, because they read a position the client wrote. MovementValidation.cpp:16-33 is a single per-packet test — cell equality plus (currentPos-newPos).SqrLength() >= 4096^2 — with no time term, no speed term and no rate limit anywhere in the C++ tree. A client sending 4000-unit steps as fast as it likes walks anywhere, through geometry, and the snap-back never fires. Every distance gate in the gamemode (playermenu.js:44 400 units, dungeons.js:450, craftedExtrasSystem.ts:469-489, gamemode.js:1521, tradeSystem, searchSystem, housingSystem) reads that position. Until movement is rate-validated, "the server checks distance" is not containment.

## The client-driven companion follow, judged against the rule

VERDICT: it half-satisfies the rule, and the half it satisfies it satisfies by accident. It must not be rolled back — the mechanism is correct and it is the only thing that makes a broken summon walk — but the decision layer has to move to the server, and one line of it is an outright bug.

DO OTHER PLAYERS SEE IT? Yes, fully, with no changes. Verified end to end: companionService.drive -> applyMovement/translateTo on the owner's client -> sendInputsService sends movement for every id in storage['hosted'] (sendInputsService.ts:110-125) -> getMovement reads the live reference position, which translateTo updates (movementGet.ts:58) -> unreliable UpdateMovement -> ActionListener::SendToNeighbours forwards the raw bytes to the companion's listeners (ActionListener.cpp:435) -> remoteServer stores form.movement -> formView's isHostedByOther branch applies it (formView.ts:455, :470). Watchers move the clone even in the worst case, because needsMove passes on horizontal error above 8 units alone (movementApply.ts:245-252) and a drive step is 34-117 units per packet. Latency to another screen is roughly 0.4-0.7 s: 250 ms drive quantisation (companionService.ts:595) + up to 130 ms send throttle (sendInputsService.ts:136) + RTT + 0.2 s interpolation horizon (movementApply.ts:213). Expect the gait to be wrong before the position is — for any non-player actor runMode and speed come from anim-graph variables, never from displacement (movementGet.ts:39, :61-62; the position-derived speed calculator is gated to formId 0x14), so a driven companion can report Standing/speed 0 while visibly sliding. Measure SpeedSampled and runMode in the npcDrift report before deciding whether that needs fixing.

SO THE RELAY HALF OF JAKE'S RULE IS MET. THE AUTHORITY HALF IS NOT:
- The latch decision, the reason for it, the trail and the step size exist on exactly one client (companionService.ts:234-239, :242, :309). The server's whole model of the companion is id/owner/target/kind/staying/leftMs, sent to one user (companionSystem.ts:482-490). Nothing in server.log distinguishes "walking normally" from "being dragged by one client".
- It is unrecoverable. The latch is keyed on the local copy and cleared on reconnect (companionService.ts:70-74, :312-316), so a relog or a host change silently reverts the companion to the broken engine follow the latch existed to work around, and no server code can take over because the server has no AI.
- There are three client-originated teleports of a server actor (setPosition past 2048 at :284-289, moveTo at :241-244 and :380-385) competing with the server's own 4096 leash (companionSystem.ts:376-380). Two authorities on one actor at different thresholds, and a client jump of 4096+ is refused by MovementValidation with no correction for a non-player actor, after which the server keeps a stale position that drives neighbour subscriptions and every isNear check.
- Single point of failure: replication exists only while the owner's client is alive, holds host and stays in the same cell. Owner alt-tabs or crashes, the companion freezes for everyone.

THE BUG, FIX IT TODAY: drive() passes healthPercentage: 1 (companionService.ts:305) into applyMovement, which was written for applying a REMOTE sample to a clone and at movementApply.ts:143-157 calls restoreActorValue for 25% of the missing health — on an actor this client hosts. The heal is then sampled straight back out by getMovement and shipped to every watcher, so everyone converges their copy to full health while the server keeps its own damage-adjudicated value. A driven companion looks unkillable on every screen and then drops dead with no warning. Fix: pass actor.getActorValuePercentage('health'), or stop routing drive through applyMovement and call translateTo directly. One line, no protocol change. Note this is a client bug, not a migration — health authority is already correct.

WHAT MOVES TO THE SERVER (and what deliberately does not):
MOVES — the verdict. companionSystem.check() already runs every 500 ms and already compares the companion's position with its owner's, and the server SetPos's the companion from the owner's hosted stream every ~130 ms. So "this companion has not closed on its owner in 3 s" is computable server-side today; the stuck detection (companionService.ts:211-232, constants at :615-619) belongs there. The driven flag becomes a field on the Companion record, echoed in sendState, so a new hoster resumes the drive and server.log can say why an actor moves the way it does. The attack-order rule ("your summon attacks what you attacked") moves next to defend() in the existing onHitDamageAttempt hook (companionSystem.ts:511-522) — the server already sees every hit, and today isValidTarget never checks that the owner hit the target, so a crafted packet points a summon at any actor within 4096 including another player. The assist auto-target becomes evidence ("this actor is in combat with me") plus a server decision. Teleports: pick one authority — the client asks for a catch-up, the server performs it with the primitive it already has. Ally setup and companion identity become neighbour-visible properties (ff_companionOf) so every client configures its copy the same way, instead of the summon being an ally to its owner and a potentially hostile NPC to everyone else.
STAYS — the locomotion. The trail's Z comes from the owner's own walked positions (companionService.ts:271-275) precisely because there is no navmesh or collision server-side; a server issuing step targets would be guessing Z, which is the floating/sinking-NPC bug family, and it could not deliver them anyway (Teleport reaches one user). Trail, translateTo, keepOffsetFromActor, the DialogueFollower alias and evaluatePackage all stay on the owner's client. The summon/vanish flash should stop being owner-only: the server knows both events exactly and already has the broadcast pattern (dboGlow in champions.js).

ONE SENTENCE FOR JAKE: the companion drive is the right shape of machine wired to the wrong brain — the client should be the hands, not the judge.

## What cannot be server-side, and why

- NPC locomotion, pathing and the step itself. There is no navmesh, collision or AI server-side — libespm parses NAVM vertices and nothing consumes them — and the only server-originated motion is MpActor::Teleport (MpActor.cpp:1635-1648), delivered to exactly ONE user via GetActorToSendTo. The server cannot walk, nudge or path anything; it can only relocate it for a single viewer and let that viewer's stream carry the result. This is the constraint every other answer lives inside, and it is why npcSpawnSystem's remedies are 'destroy and re-place' rather than a walk.
- The companion drive's step targets and their Z. companionService.ts:271-275 takes each step's height from the trail of the owner's own walked positions, precisely because the server has no ground. A server issuing step targets would be guessing Z, which is the existing floating/sinking-NPC bug family, and it could not deliver them anyway. The VERDICT to drive moves to the server; the trail and translateTo stay on the client.
- Collision and line of sight, and therefore crosshair target selection. Game.getCurrentCrosshairRef() (playerActionService.ts:92-131) has no server equivalent and never will. The client names a target and the server bounds it — but be clear that the bound is only as trustworthy as the position it reads, so this is contained only once movement is rate-validated.
- Animation playback and behaviour-graph variables. The server never generates an animation; it forwards the bytes a client sent and stores the last one. runMode, direction and speed for any non-player actor come from anim-graph variables, never from displacement (movementGet.ts:39, :61-62). A driven actor can therefore report Standing while visibly moving — the position is honest, the gait is not.
- Detection of environmental events: fall damage, trap damage, hazards, anything an engine script produces. No collision, no physics, no scripts server-side, and fall damage fires no hit event at all. The client is the only witness. Note the split carefully: the OBSERVATION cannot move, the damage number and the kill must.
- Engine-computed personal mechanics keyed on local actor values — spell magicka cost, tempering and potion quality, lockpicking, sneak detection. These are computed by the engine on the character's own client, and magicka and stamina are not even relayed between clients, so the local SetActorValue from masterySystem is the only mechanism and it works. Only the combat half of mastery is inert and only the combat half should move.
- Quest-alias follow: DialogueFollower's forceRefTo, evaluatePackage and the navmesh walk they produce (companionService.ts:404-437). Aliases and packages exist only in the engine. Two things about it are NOT engine facts and should be reported to the server: the verdict that the alias failed, and that the two vanilla slots are a client-global resource shared with any real hired follower.
- Deleting engine-created local references. WorldCleanerService picks victims with Game.findRandomActor from the local engine, and most of what it eats has no server form at all — the clearest case is the player's own vanilla summon, created locally by their spell, which companionService deliberately sweeps: the server has never heard of that reference and no packet can name it. The sweep stays; the protection list and the reporting move.
- The chicken-anomaly refs specifically. worldCleanerService.ts:94 records that these refuse to Disable when the game loads near them, and a server-issued disable of an espm ref arrives as that same engine Disable on each client — so it would fail for exactly the case the workaround exists for. The authoritative layer here is the ESP under the standing 'server spawns all actors' rule, not the server process. Keep the client fallback, but drop the per-session initialPos keying.
- Per-frame voice attenuation. Gain is applied per listener inside a browser audio node the server has no path to, and a hard subscribe/unsubscribe at the configured whisper range (140 units, 2 m) would renegotiate WebRTC on practically every step and clip the first words of every line. The server owns a coarse subscription envelope; the client keeps the fine attenuation inside it.
- Observing map-marker discovery and learned ingredient effects. These arrive through client-only engine events (locationDiscovery, cellFullyLoaded, equip, crafting menu close) with no server equivalent and no espm path, and the server could never verify a claimed discovery. The client observes and re-applies; the server holds the record for portability.
- Writing anything into the engine at all. The server can only send data. Every visible effect — a pose, a control lock, an equip, a shader, a game hour, a position — is executed by a client. 'Server-side' can never mean 'the server did it to the game'; it means the server decided it and every client was told.

## Migrations, ordered by multiplayer risk

### 1. Offline-mode login identity: the client names its own profileId and the server spawns it as that account, with no session, token, HWID or IP binding — and profileId 1 is a full admin.

- **From -> to:** client-asserted identity in gameData -> server-assigned session identity
- **How:** VERIFIED LIVE: server-settings.json has offlineMode true and adminProfileIds [1]; login.ts:272-277 takes gameData.profileId straight from the client (authService.ts:136-140 reads it out of the player's own settings file) and emits spawnAllowed with it; the ban check, Discord membership check and guid re-check all live in the offlineMode===false branch above. adminRoles.ts:42-44 short-circuits to tier "senior" on that profileId before it ever looks at private.discordRoles, so profileId:1 is admin takeover, and gamemode.js:653 gates the audit mirror on the same isAdmin() so a forged login writes a clean audit trail. Fix in login.ts: in offline mode, bind the profile to something the server controls — issue a per-install secret on first connect and store it server-side keyed by profileId, refuse a profileId whose secret does not match, and refuse any profileId in adminProfileIds unless it also carries that secret. Cheaper interim: drop adminProfileIds entirely and drive admin tier only from private.discordRoles.
- **Needs C++:** no  **Effort:** small (one file, server ts) for the admin half; medium for real per-profile secrets
- **Risk if skipped:** Any player logs in as any other character — their inventory, gold, housing, mastery and faction ranks — or as a senior admin, by editing one integer in a settings file. No patched bundle required. listenHost 127.0.0.1 is the only thing containing it; the moment the port is exposed for remote play (DEPLOYMENT.md) the server has no authentication at all. This blocks remote play and must land before it.

### 2. Movement has no rate or speed validation, only a per-packet delta test — so the position every server-side proximity rule reads is whatever the client last wrote.

**BUILT 2026-09-19, branch `movement-rate-validation`, not yet running on the server.** `MovementValidation`
now keeps the last position it accepted per player actor plus a token bucket of movement allowance
(`MovementLimits`, from `server-settings.json` `movementValidation`): the bucket refills at the speed
ceiling, a packet spends the distance it claims, and a packet that cannot pay is refused with the existing
`isMe` snap-back, rate limited to one per 250 ms. Horizontal, upward and downward budgets are separate
because falling is fast. The ceilings come from the engine's own MOVT records read out of the load order
(`NPC_Sprinting_MT` 500 u/s forward is the player sprint, `Horse_Sprint_MT` 600, `Horse_Default_MT` 450 run,
`NPC_Default_MT` 370 run / 80 walk; `fJumpFallVelocityMin` 700 is where fall damage starts), so the first
ceiling is 1000 horizontal, 2000 up, 4000 down with a 3 s burst, to be tightened from the measured log.
Three things make it safe to ship: `"enforce": false` logs what it would refuse and changes nothing, a
server teleport is detected by the server's own position having moved since the last accepted packet (which
covers `MpActor::Teleport`, door activation, respawn, change-form load and every `mp.set locationalData`)
and opens a 5 s grace in which the player's in-flight packets are dropped without a snap-back, and the
check is skipped entirely for hosted NPCs, because refusing an NPC's move with no correction path is the
frozen-copy bug in C++ task 1. A player's own movement is now validated BEFORE `SendToNeighbours` relays
it, so a refused packet no longer reaches other clients; hosted actors keep the old order.

- **From -> to:** client-authored position accepted at any rate -> server-rate-validated position
- **How:** VERIFIED: MovementValidation.cpp:16-33 is the whole check — cell equality plus (currentPos-newPos).SqrLength() >= 4096*4096, with the TeleportMessage2 snap-back gated on isMe. There is no time term, no speed term, and ActionListener.cpp:421-500 records lastMovUpdateByIdx only for host timeouts; a grep for ratelimit/throttle/flood across the C++ tree returns nothing. Add to MovementValidation::Validate a per-actor time-aware check: keep the last accepted position and timestamp, compute units/second, and refuse (with the isMe snap-back) anything above a generous ceiling — sprint-plus-horse plus slack, tuned from a real log before picking the number. Keep the existing 4096 delta as the hard ceiling for a single packet.
- **Needs C++:** yes  **Effort:** medium — C++ change, CI flatrim or Native build, per fork\CLAUDE.md
- **Risk if skipped:** Teleport, speedhack and noclip in one, since there is no server-side collision. It also dissolves every distance gate in the gamemode — playermenu.js:44 (400 units), dungeons.js:450 entrance reach, craftedExtrasSystem.ts:469-489, gamemode.js:1521 skinning, tradeSystem, searchSystem, housingSystem — because each reads a position the claimant authored. Until this lands, 'the server re-checks distance' is not a containment argument and should not be cited as one.

### 3. Host assignment is a first-packet-wins race between clients with no server policy — and host is the key to moving an actor, hitting with it, casting with it and activating refs as it.

- **From -> to:** client race -> server policy in mp.onHostAttempt
- **How:** formView.ts:852-866 calls tryHost(remoteId) once a second for any streamed actor with no visible driver; ActionListener.cpp:1083-1100 grants to whoever asks when hoster==0 or the current hoster has been silent for 2 s, with the gamemode's onHostAttempt hook (checked first at :1078-1081) the only gate — and today that hook only reserves companions (companionSystem.ts:505-509). Extend it into a general policy in the gamemode: requester must be online, in the same worldOrCell as the actor, within a sane radius, not restrained, and not already hosting more than N actors. This is JS only — the hook already fires ahead of the hosters map write. Log every grant and every denial so host churn becomes visible in server.log.
- **Needs C++:** no  **Effort:** small — one handler in the gamemode layer, hot-reloads
- **Risk if skipped:** Desync: the same bandit fights differently depending on who got there first, and a host change mid-fight restarts its AI for everyone. Cheat: tryHost takes a bare remote id, so a modified client can claim any unattached reference in the world and then move it, report hits with it as aggressor (the server re-checks only the hosters map, ActionListener.cpp:1441-1456), cast spells as it and activate refs as it (:825 checks only hosterId). This is the single largest unmediated client decision in the layer, and it is the cheapest to fix.

### 4. Damage trigger integrity: the two hit multipliers that favour the attacker are taken from the client verbatim, and bow/crossbow hits are exempt from the only range check while the melee reach test is commented out.

- **From -> to:** client-asserted attack modifiers and unbounded reach -> server-derived
- **How:** VERIFIED: TES5DamageFormula.cpp:151-163 applies damage *= 2.f on hitData.isPowerAttack and damage *= 1.3f on isSneakAttack, both copied straight off the engine HitEvent (hitService.ts:66-67) and never re-derived — a flat 2.6x for a two-line client edit. The author knew the difference: isHitBlocked is overwritten server-side at ActionListener.cpp:2070 after the server's own ShouldBeBlocked test. Range: ActionListener.cpp:1493-1506 skips the 4096-unit check entirely when IsBowOrCrossbowShot (verified at :1346-1371, and it decides partly from the client-supplied isBashAttack), and the real reach test at :2003-2023 is a commented-out block behind '// TODO: repair IsDistanceValid instead'. Fix in C++: drop the sneak multiplier or gate it on a server-side detection proxy; keep power attacks but rate-limit them against the existing CanHit weapon-speed timer; give bow shots a generous but finite range instead of exemption. INTERIM WITH NO REBUILD: clamp the final number in the gamemode's onHitDamageAttempt hook, which already exists and already fires (adminSystem.ts:798-801, companionSystem.ts:511-522).
- **Needs C++:** yes  **Effort:** medium for the C++; small for the gamemode clamp, which should land first
- **Risk if skipped:** 2.6x damage in PvE and PvP for a trivial client edit, plus a 58-metre melee reach hack and, with a bow equipped, the ability to hit any actor anywhere in the same cell or worldspace with no line of sight. The resulting damage is fully adjudicated and applied by the server, so it is indistinguishable from legitimate damage in any log.

### 5. Damage REPORTING is client-triggered and gated on host, so a player who hosts the NPC fighting them is the sole reporter of damage against themselves.

- **From -> to:** sole client trigger -> client reports, server corroborates and rate-limits
- **How:** hitService.ts:12 is the only producer of MsgType.OnHit in the codebase — the server never originates damage — and :21 gates sending on isHostedByMe(aggressor). A player alone with a hostile NPC is normally that NPC's hoster, so deleting one emit makes them immune to every NPC they host, permanently and silently; deathService.ts:102-113 then keeps them alive locally because the server agrees they are alive. Health reporting is genuinely defended (CropRegeneration caps upward reports to the natural regen rate), which is exactly what makes this the live hole: the server will never reduce health it was never told to reduce. Mitigations that need no C++: the host policy above (deny host of an actor that is in combat with the requester, hand it to another nearby client, or refuse host so nobody drives it), plus a server-side watchdog in the gamemode — an NPC that has been hostile and adjacent to a player for N seconds with zero inbound OnHit from that player's client is a reportable anomaly.
- **Needs C++:** no  **Effort:** medium — policy plus watchdog in the gamemode layer
- **Risk if skipped:** Silent, total PvE immunity for anyone who edits the bundle, with no packet, no anomaly and nothing in server.log. It is the mirror image of the host problem and is fixed by the same lever.

### 6. Proximity voice: every player joins one LiveKit room with full subscribe rights and audibility is a gain stage on the listener's own machine.

- **From -> to:** client-side attenuation as the only gate -> server-driven subscription envelope, client keeps the fine attenuation
- **How:** VERIFIED: voiceSystem.ts hand-mints the JWT with crypto.createHmac and grants video:{roomJoin,canPublish,canSubscribe,canPublishData} for room 'dragonbreak'; voiceService.ts:296-322 pushPeers computes distances from the client's own world model and hands them to the browser. There is no LiveKit server SDK in this tree, so the fix means adding a RoomService client, not flipping a flag. Do NOT gate at the configured mode ranges — whisper is 140 units (2 m) and a hard subscribe/unsubscribe there would renegotiate WebRTC on practically every step and clip the first words of every line. ### 27. Two shared-file hazards in the spawn pipeline, and two floating-NPC detectors that cannot see each other.

- **From -> to:** housekeeping, not a client/server split
- **How:** CORRECTION: the lost-update race between wildlife.js and dungeons.js on NPC-Spawns.json cannot occur as described — writeZones (wildlife.js:57-73) and writeSpawnZones (dungeons.js:121-132) are fully synchronous readFileSync/filter/writeFileSync/renameSync with no async or await in either file, so in single-threaded Node nothing can interleave, and each preserves the other's prefix. The real hazards are different: both write the same temp path SPAWNS_FILE + '.tmp', which collides the moment a ck-mcp generator writes from another process, and a dungeons.js write while ST.leases is empty drops every dungeon zone — ST survives reloads on globalThis but a fresh boot with an interrupted lease does not. Give each writer its own temp name and guard the empty-lease write. Separately, the two drift detectors disagree by design: hostedDriftService re-seats the reference in place under a 10 s client-local cooldown while npcSpawnSystem destroys and respawns the actor, the client's finding reaches the server only as a log line (gamemode.js:1142-1144), and a host change silently resets the client's attempt counters. Report the client's repair as real data and let npcSpawnSystem hold off on an actor a client just fixed.
- **Needs C++:** no  **Effort:** trivial for the temp paths; small for the drift reporting
- **Risk if skipped:** NPCs silently missing for everyone in a dungeon lease with nothing in the log to say why, and floating NPCs repaired by whichever of two incompatible remedies happens to reach them first — including the server destroying an actor the client has just fixed, with the client unaware its target was replaced.

### 28. A client that cannot resolve an NPC's base form renders nothing and never says so; and the dungeon glow 'off' fan-out silently misses members without a live actor.

- **From -> to:** silent client failures -> reported and reconciled
- **How:** formView.ts:141-151 falls through getLeveledBase (dead code, 'crashes too often ATM'), Game.getFormEx(model.baseId) and the appearance base, then does a bare `return` with no log — so a player with a drifted Plugins.txt or a missing plugin simply does not have that NPC, indistinguishably from the NPC not existing. Given the known Vortex Plugins.txt drift this is a live failure mode: report the unresolved baseId so the server can log it. Separately, dungeons.js:425 and :434 fan the glow-off out with actorByProfile, which returns 0 for a member mid-login or mid-respawn, and DboGlowService has no send path and no reconciliation — add a periodic glowLease resend or a client request on stream-in.
- **Needs C++:** no  **Effort:** small
- **Risk if skipped:** Invisible per-client world gaps that look like server bugs and cost hours to diagnose, and one party member who keeps seeing a chest lit that the party already emptied.

### 29. Blocked spells still take effect on the caster; only replication is refused.

- **From -> to:** post-hoc cast filter -> remove the spell from the actor
- **How:** ActionListener.cpp:1637-1643 checks IsSpellBlocked and returns BEFORE SendToNeighbours and before the gamemode's onSpellCast — but the engine has already cast it locally by then. For the racial powers this list exists to suppress, the caster still gets the self-buff (Highborn, Histskin, Berserker Rage) on their own screen, invisible to everyone else, and MasterySystem never sees the cast because the gamemode event is skipped with it. Strip the spell from the actor server-side with RemoveSpell, which is registered, instead of filtering the cast after the fact.
- **Needs C++:** no  **Effort:** small — gamemode side, using an already-registered Papyrus call
- **Risk if skipped:** A blocked power is still a power, just an unreplicated one, and the block behaves differently from what server-settings.json implies to whoever maintains it.
